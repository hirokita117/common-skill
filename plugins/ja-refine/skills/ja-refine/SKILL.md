# ja-refine

LLM が生成した日本語を、4つの外部 skill を決まった順に適用して、理解しやすい日本語に直す。
この skill 自身は文章の規範を持たない。持っているのは、モードの判定、適用する順序、skill どうしの規則がぶつかったときの決め方、ファイルの扱いの4つである。

依頼: $ARGUMENTS

## 使う skill

次の4つを Skill ツールで呼び出す。
呼び出し名は導入方法によって変わるので、利用可能な skill の一覧にある名前を、左の候補から順に探して使う。

| 役割 | skill | 呼び出し名の候補 |
|---|---|---|
| 段落と論証の構成、読み手の負荷、冗長さ | japanese-tech-writing | `japanese-tech-writing:japanese-tech-writing`、`japanese-writing-skills:japanese-tech-writing`、`japanese-tech-writing` |
| 読み物としての緩急 | cognitive-rhythm-writing | `cognitive-rhythm-writing:cognitive-rhythm-writing`、`japanese-writing-skills:cognitive-rhythm-writing`、`cognitive-rhythm-writing` |
| 語句と文の不自然さ（lint つき） | natural-japanese | `natural-japanese:natural-japanese`、`natural-japanese` |
| 最終の推敲と、原文から意味が変わっていないかの検査 | yomiyasu | `yomiyasu:yomiyasu`、`yomiyasu` |

一覧にない skill があれば、作業を始める前にその名前を利用者に伝える。
残りの skill で続けるか、先に導入するかは利用者が決める。導入方法は次のとおり。

```
/plugin marketplace add hirokita117/common-skill
/plugin install ja-refine@common-skill
```

4つとも見つからないときは、文章には手を付けずに終える。規範なしで自己流に書き直すことはしない。

## モードの判定

次の順で決める。上の項目で決まれば、下は見ない。

1. 引数の先頭が `doc` または `blog` なら、それに従う。
2. 依頼文が文書の種類や読み手を述べていれば、下の表で判定する。
3. 依頼文で決まらなければ、対象の文章の中身を表で判定する。
4. それでも決まらない、または両方の特徴が混ざっているなら、doc モードにする。

| | doc モード | blog モード |
|---|---|---|
| 文書の例 | 設計書、仕様書、手順書、報告書、議事録、提案書、稟議書、障害報告、README、PR の説明文、論文、技術書の原稿 | ブログ記事、note、技術ブログ、エッセイ、コラム、広報記事、SNS 向けの長文 |
| 読み手 | 特定できる。同じ組織の人、同じ分野の専門家、決裁者 | 特定できない。通りすがりに読む人を含む |
| 読まれ方 | 必要があって読む。あとで参照される | 読むかどうかを読み手が選ぶ。途中でやめられる |
| 目指すもの | 誤読されないこと、すぐ要点に届くこと | 最後まで読み進められること |

モードを決めたら、文章を直し始める前に、どちらのモードで動くかとその理由を一文で利用者に伝える。
利用者がモードを指定していない場合は、もう一方のモードに切り替える方法（`/ja-refine blog <対象>` のような指定）も添える。
モードについて質問はしない。迷ったら doc モードで進める。

## 全体を通して守ること

4つの skill はそれぞれ独自の規則を持ち、いくつかは互いに逆を向く。
ぶつかったときは、次の順で上にあるものを優先する。

1. **意味を変えない。** 原文にある主張、事実、数値、固有名、条件、確信の度合いを保つ。原文にない情報を足さない。どの skill の規則であっても、これに反する直し方は採らない。数値や事実が誤りに見えても直さず、報告で伝える。
2. **原文の文体を保つ。** です・ます体とである体、敬語の度合い、表記の方針、改行の入れ方は原文に合わせる。
3. **構成を変えるのは段階1だけにする。** 見出しの文言、節の数と順序、段落の分け方は段階1で決め、あとの段階では動かさない。段階1でも、節の順序と数は変えない。見出しは、何の節か読み取れないものに限って直し、直すのは3か所までにする。
4. **前の段階が意図して置いた表現を、後の段階が打ち消さない。** とくに blog モードで段階2が置いた短い文、問いかけ、判断の保留は、段階3と段階4で「不要な演出」として削らない。削ってよいのは、優先順位1に反する場合だけである。
5. **モードが許していない表現は足さない。** doc モードでは、修辞疑問、読者への呼びかけ、溜めを新しく足さない。

各 skill を呼び出すときは、次の3点をその skill への依頼として明示する。

- ほかの skill の途中で動いていること。利用者への質問はせず、確かめたい点は記録して返すこと。
- 返すのは直した本文と、変更点・確認事項の記録であること。
- 上の優先順位1〜5。

各 skill が利用者に確かめたいとした点は、その場で質問せずに集めておき、最後の報告でまとめて伝える。
例外は、文章の主旨が2通りに読めて、どちらかに決めないと直せない場合だけである。この場合は段階1の前に1回だけ質問する。

## 作業ファイルの準備

1. 対象を決める。引数や依頼文にファイルのパスがあればそのファイル、貼り付けられた文章があればその文章を対象にする。どちらもなければ、対象を利用者に尋ねる。対象が複数あるときは、1つずつ順に処理する。
2. 作業用のディレクトリを、スクラッチパッドがあればその中に、なければ `mktemp -d` で作る。プロジェクトの中には作らない。
3. 対象をそこに `original.md` として写す。これは最後まで書き換えない。意味が変わっていないかを検査するときの基準にする。
4. 同じ内容を `work.md` として写す。各段階はこのファイルを直す。

対象が Markdown でないときは、拡張子を原文に合わせる。

## 手順

### 段階1: 構成と論証を直す（japanese-tech-writing）

japanese-tech-writing を呼び出し、`work.md` に適用する。
扱うのは、段落の切り方、論証の順序と厳密さ、読み手の負荷、冗長な繰り返し、中身のない言い回し、翻訳調の比喩である。

この skill は技術書の原稿を想定して書かれている。対象が議事録や稟議書のように論証を持たない文書のときは、当てはまる規則だけを使い、書籍に固有の規則（章をまたぐ伏線、架空の例の扱いなど）は当てはめない。

### 段階2: 緩急を設計する（cognitive-rhythm-writing）— blog モードだけ

doc モードでは、この段階を飛ばす。

cognitive-rhythm-writing を呼び出し、`work.md` に適用する。
この skill は japanese-tech-writing を先に読むことを求めている。段階1で読み込み済みなので、その要求は満たしたものとして扱う。

緩急の材料は、原文にすでにある出来事、データ、書き手の判断だけから取る。
原文にない体験談、感想、場面を作って足すことは、優先順位1に反するので行わない。
材料が足りない箇所は、平坦なまま残す。

### 段階3: 語句と文を直す（natural-japanese）

natural-japanese を呼び出し、`work.md` に適用する。
コマンドは既定（書き直し）を使い、`score` は使わない。深さは `quick` を既定とし、利用者が「しっかり」「念入りに」と頼んだとき、または対外向け・経営向けの文書のときは `full` にする。`full` にするときは、時間がかかることを先に伝える。

モードごとの指定は次のとおり。

| | doc モード | blog モード |
|---|---|---|
| lint の `--genre` | 技術文書は `tech`、それ以外は `business` | 技術ブログは `tech`、それ以外は `essay` |
| 文書タイプ | 報告書、ガイド、メモ、議事録、スライドのうち近いもの | 近いものがなければ指定しない |

元の文書との比較が必要な検査（原文にない事実の混入を調べるものなど）には、`original.md` を元として渡す。
natural-japanese が同梱する critical-thinking は呼び出さない。論旨そのものの検査は、この skill の範囲に含めない。

### 段階4: 最終の推敲と検査（yomiyasu）

yomiyasu を呼び出す。yomiyasu は名前を出して頼まれたときだけ動く skill なので、「yomiyasu で推敲する」と明示して呼ぶ。

- 推敲の対象は `work.md` とする。
- 最終稿は作業用ディレクトリの中に保存させる。
- 原文と最終稿を比べる検査では、原文として `original.md` を渡す。これで、段階1から段階4までの全体を通して意味が変わっていないかを確かめられる。
- 実行記録は作業用ディレクトリに置かせる（検査コマンドに `--state-dir <作業用ディレクトリ>` を付ける）。プロジェクトに `.yomiyasu/` を作らせない。記録を作らない指定（`--no-record`）は、提出前の照合が実行されなくなるので使わない。
- 「本文だけ」を返すよう頼む。確認事項は記録として受け取る。

モードごとの指定は次のとおり。

| | doc モード | blog モード |
|---|---|---|
| 種類 | `formal`、`proposal`、`incident`、`manual`、`minutes`、`paper`、`pr`、`slides`、`mail` のうち近いもの | 技術ブログは `article`、読み物は `essay`、紹介・告知は `promo` |
| 読み手 | 専門家向けは `expert`、社内の関係者向けは `informed` | `general` |

検査で意味の変化が指摘されたら、その箇所を原文の意味に戻す。戻したあとは、yomiyasu の手順に従って検査をやり直す。
この段階のあとで本文を変えない。変えた場合は、段階4の検査をもう一度通す。

### 段階5: 書き戻しと報告

対象がファイルのとき:

1. 書き戻す前に、原文が git で復元できるかを調べる。git の管理下にあり、未コミットの変更がなければ、復元できる。
2. 最終稿で原文のファイルを上書きする。
3. 復元できる場合は、作業用ディレクトリを削除する。復元できない場合は、`original.md` を残し、その絶対パスを報告に書く。

対象が貼り付けられた文章のときは、最終稿を返答に載せ、作業用ディレクトリを削除する。

各 skill が独自に作った中間ファイルは、プロジェクトに残さない。

最後に、次の内容を1つの報告にまとめる。各 skill の報告をそのまま並べない。

- 使ったモードと、その理由
- 通した段階と、飛ばした段階（導入されていなかった skill、動かなかった検査スクリプトを含む）
- 主な変更点を数点
- 意図して直さなかった箇所と、その理由
- 書き手に確かめたい点（各 skill から集めたもの。数値や事実の誤りに見える箇所を含む）
- 上書きしたファイルのパスと、原文の戻し方

報告の文章にも、段階3と段階4の規則を当てる。

## 例

| 依頼 | モード | 理由 |
|---|---|---|
| `/ja-refine docs/design.md` | doc | 設計書であり、読み手が特定できる |
| `/ja-refine blog posts/2026-11-release.md` | blog | 引数で指定されている |
| 「note に載せる記事を読みやすくして」と本文の貼り付け | blog | 依頼文が不特定多数向けの媒体を述べている |
| 「これを読みやすくして」と社内向けのお知らせの貼り付け | doc | 依頼文では決まらず、中身が社内文書である |
| 「この文章を直して」と種類の分からない文章 | doc | 判定できないので既定に従う |

## うまく動かないとき

- **skill が見つからない**: 「使う skill」の節のとおり、足りない skill の名前と導入方法を利用者に伝える。
- **スクリプトが動かない**: natural-japanese は `uv` を、yomiyasu は Python を使う。動かないときは、各 skill が定めている代替の手順（目視での点検）に従い、報告の「飛ばした段階」に書く。検査ができなかったことを伏せて、検査済みのように報告しない。
- **段階4の検査が意味の変化を指摘し続ける**: 指摘された箇所を原文の表現に戻す。読みやすさより、意味を保つことを優先する。
- **文章が長く、途中で中断した**: `work.md` が残っていれば、終わった段階の次から再開する。残っていなければ、原文から段階1をやり直す。
